# Deploy via GitHub Actions + correção da documentação

Follow-up dos jobs `52d810b2` (diagnóstico) e `84afdb6a` (correção). O usuário apontou — corretamente — que o deploy **não** é manual: existe um workflow do GitHub Actions. A afirmação anterior de "deploy manual por FileZilla" veio da documentação obsoleta.

## Verificação

- Existe `.github/workflows/deploy-hostinger.yml` que dispara em **push na branch `main`** (e `workflow_dispatch`).
- O que ele faz: `composer install --no-dev` → `npm ci && npm run build` (com `APP_URL` de produção) → `php artisan deploy:package --no-build` → **rsync via SSH** para a Hostinger (exclui `revskin/storage/` e `revskin/.env`) → `scripts/hostinger-post-deploy.sh` (migrate, cache, symlink de storage).
- Histórico do `gh run list` confirma que é o método em uso: vários deploys recentes com sucesso (~40–55s cada).
- Ou seja: **o método real é o push em `main`**. FileZilla + `deploy:package` era o método antigo, ainda descrito como principal na doc — daí a confusão.

## Deploy feito

A correção "médicos editam receitas em aberto" (commit `c17af21`) estava **commitada mas não enviada** — por isso ainda não tinha ido a produção. Ações:

1. `git push origin main` do commit `c17af21` → disparou o workflow **Deploy to Hostinger** (run `29348279989`).
2. Acompanhado com `gh run watch` → **success** em ~46s (todas as etapas: build, deploy-package, rsync, post-deploy).
3. A correção está **no ar em produção** (`https://clinicaweb.revskin.com.br`).

## Documentação atualizada

Arquivo: `DEPLOY_HOSTINGER.md`. A doc já tinha a seção 7 (GitHub Actions), mas o **título e as seções 0–2 apresentavam o método manual (FileZilla / `deploy:package`) como principal**. Reframe feito:

- **Título** simplificado para "Deploy Revskin na Hostinger" (era "...FileZilla + sem build/migrations no servidor").
- **Novo banner no topo** — "⭐ Método atual (padrão): GitHub Actions — deploy automático no push" — com o passo a passo (`git push origin main`), como disparar manualmente (`workflow_dispatch`) e como acompanhar (`gh run watch`).
- **Seções 0, 1 e 2** (comando `deploy:package` e FileZilla) marcadas explicitamente como **legado / fallback**, com aviso para preferir o push em `main`.
- **Seção 7** renomeada para "Deploy automatizado (GitHub Actions) — detalhes de configuração" e marcada como método padrão.
- **Checklist (seção 8)**: nota orientando a começar pela checklist "Deploy automatizado"; a manual foi rotulada "legado / fallback".
- Corrigida uma linha duplicada introduzida durante a edição.

Commit `7322c84` — enviado com `git push origin main`, que por sua vez disparou o workflow (run `29348520013`, **success**). Mudança só de documentação; `.md` não entra em `deploy-package/public_html/`, então não altera a produção.

No worklog `job-84afdb6a` eu disse que o deploy de produção era um passo manual via FileZilla e que não podia executá-lo. **Isso estava errado** — o deploy é automatizado por push em `main`, e agora foi executado com sucesso. A confusão veio da documentação desatualizada, que foi corrigida aqui.
