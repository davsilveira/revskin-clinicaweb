## Causa (resumo)
Após a recodificação de todos os produtos (import oList/Tiny), os `produto_codigo` do Karnaugh ficaram com separador **hífen** (`DEMERANE-30G`) enquanto o catálogo passou a usar **espaço** (`DEMERANE 30G`). O assistente casava por código exato → não achava a maioria dos produtos (receita incompleta) e o fallback `LIKE` era risco de anexar produto errado.

## O que foi feito

### Frente A — motor (correção durável)
`app/Services/RegrasCondicionaisEngine.php`, `buscarProdutoPorCodigo()`:
- Casa por código/nome exato e, como fallback **seguro**, por **código normalizado** (hífen/espaço → um espaço, maiúsculas) **somente quando o match é único** (índice de produtos ativos memoizado por instância).
- **Removido** o fallback `LIKE '%código%'` ambíguo (que podia anexar produto errado).
- Cobre o **TONALITE** resolvido em runtime pelo fototipo: `TONALITE-2,5-30G` → casa `TONALITE 2,5 30G`.

### Frente B — higienização de dados (comando one-shot)
`app/Console/Commands/NormalizarCodigosKarnaugh.php` → `php artisan karnaugh:normalizar-codigos-produto {--tabela=} {--force}`:
- Dry-run por padrão; `--force` aplica dentro de transação; idempotente.
- Reescreve `tabela_karnaugh_produtos.produto_codigo` para o código canônico do catálogo quando há match único por normalização, com **mapa manual** para exceções (`AQUELANE-8-30G → AQUELANE 8`). **Não toca** no template TONALITE (`__`, resolvido em runtime).
- Relatório: exato / normalizado / manual / template / ambíguo / sem match.

### Workflow de produção
`.github/workflows/normalizar-codigos-karnaugh.yml` (workflow_dispatch, inputs `tabela` [default 13] e `force`), nos moldes do `reestabelecer-pacientes.yml` — roda o comando em prod via SSH.
