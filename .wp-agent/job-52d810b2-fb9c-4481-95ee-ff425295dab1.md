# Diagnóstico: médicos não conseguem editar receitas em aberto

**Modo:** verificação apenas — nenhum arquivo foi alterado.

## Conclusão

Não é problema de permissão de rota. O bloqueio é **intencional e está codificado no método `edit`** do `ReceitaController`: qualquer usuário com papel `medico` é redirecionado para a tela de **visualização** (`receitas.show`) ao tentar abrir o formulário de edição — independentemente de a receita estar "em aberto" (aberta/rascunho). Só admins chegam ao formulário editável.

## Onde está

`app/Http/Controllers/ReceitaController.php` — método `edit()` (linhas 242–254):

```php
public function edit(Request $request, Receita $receita): Response|RedirectResponse
{
    // Redirect finalized prescriptions to view – they are not editable
    if ($receita->status === 'finalizada') {
        return redirect()->route('receitas.show', $receita);
    }

    if ($request->user()->isMedico()) {          // <-- AQUI
        return redirect()->route('receitas.show', $receita);
    }

    return $this->renderReceitaForm($receita, $request, viewMode: false);
}
```

O segundo `if` redireciona todo médico para a visualização, sem checar o status da receita. Ou seja, mesmo receitas "em aberto" ficam somente-leitura para médicos.

### Origem da mudança

Introduzido no commit **a45d084** (13/04/2026):

> `fix(receitas): anotações internas só para não-médicos; médico só visualiza`

Foi uma decisão deliberada de tornar o médico "somente visualização" nas receitas. É a causa direta do sintoma relatado.

## Por que não é a rota nem o `update`

- **Rota** (`routes/web.php:91-96`): o grupo usa o middleware `medico` = `EnsureUserIsMedico`, que **permite** admin **e** médico. Então médicos passam pela rota sem problema.
- **`CheckRole` / middleware `medico`**: nenhum deles barra o médico aqui.
- **Método `update()`** (`ReceitaController.php:403-418`): também **não** bloqueia médicos — só barra receitas `finalizada` ou com atendimento `em_producao`/`finalizado`. Portanto o bloqueio é exclusivamente o redirect dentro de `edit()`; o médico simplesmente nunca chega ao formulário para enviar o `PUT`.
- `isMedico()` (`app/Models/User.php:83-86`) retorna `true` apenas para `role === 'medico'` (admin não é médico), por isso admins escapam do redirect e conseguem editar.

## Arquivos relevantes (não modificados)

- `app/Http/Controllers/ReceitaController.php` — método `edit()` (bloqueio) e `update()` (sem bloqueio).
- `routes/web.php:90-98` — grupo de rotas de edição de receitas.
- `app/Http/Middleware/EnsureUserIsMedico.php` — permite admin + médico.
- `app/Models/User.php:78-106` — helpers de papel (`isAdmin`, `isMedico`, etc.).

## Como validar manualmente

Ambiente: `https://revski-main.ddev.site:33177`

1. Faça login com um usuário de papel **médico**.
2. Acesse `/receitas` e abra uma receita com status **aberta**.
3. Vá para `…/receitas/{id}/edit`.
4. **Comportamento atual (bug):** você é redirecionado para `…/receitas/{id}` (tela de visualização), sem poder editar.
5. Repita com um usuário **admin**: o formulário de edição abre normalmente para a mesma receita — confirmando que o bloqueio atinge só médicos.

## Correção sugerida (para uma futura implementação, se aprovada)

Remover ou condicionar o `if ($request->user()->isMedico())` em `edit()` para não bloquear receitas em aberto — por exemplo, deixar passar quando `$receita->status !== 'finalizada'`. Convém confirmar com o negócio se a decisão do commit a45d084 (médico só visualiza) deve ser revertida ou apenas afrouxada para receitas em aberto.
