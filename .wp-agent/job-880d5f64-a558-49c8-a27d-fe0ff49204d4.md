# Worklog — Dados do médico (CRM etc.) somem ao trocar de médico para outro perfil

Job: `880d5f64-a558-49c8-a27d-fe0ff49204d4`
Env: `revskin-main` — https://revski-main.ddev.site:33177
Follow-up do job `097d9d9d-...` (pacientes perdiam o vínculo).

## Pergunta investigada
"Quando mudamos o usuário de médico para outra coisa, os dados dele somem (ex.: CRM).
Teria como não remover eles? Precisei mudar médica → admin → médica e deu esse problema."

## Diagnóstico — é a MESMA causa raiz do job anterior
Os dados profissionais (CRM, UF, especialidade, telefones, endereços, assinatura) ficam no
registro da tabela `medicos`, e o usuário os enxerga através da relação `user->medico`
(FK `users.medico_id`).

O código **nunca apagou** o registro em `medicos` na troca de papel. O que acontecia:

- `UserController::update()`, no ramo não-médico, fazia `'medico_id' => null`.
- Isso **desconectava** o usuário do registro de médico. O registro continuava no banco,
  mas `user->medico` passava a retornar `null`.
- No painel de usuários (`resources/js/Pages/Users/Index.jsx`, `openEditDrawer`) os campos
  de CRM/UF/especialidade são pré-preenchidos a partir de `user.medico`. Com `user.medico`
  nulo, apareciam **em branco** → sensação de que "os dados sumiram".
- Ao voltar para médico, como `user->medico` era null, era criado um **médico novo e
  vazio** (`MedicoService::create`), e o registro antigo (com o CRM real) ficava órfão.

Ou seja: os dados não eram deletados, eram **desvinculados**. O sintoma "CRM sumiu" e o
sintoma "pacientes sumiram" têm a mesma origem.

Confirmado que não há outro caminho que apague o médico na troca de papel: não há observer
de `Medico`, nem `delete`/`destroy` no fluxo. O único `medico_id => null` remanescente em
`UserController` é a guarda de órfão (linha ~212, só dispara quando o `medico_id` aponta
para um registro já inexistente). `AuditMedicoLinks` é comando de manutenção à parte.

## Correção — já aplicada no job anterior, cobre também este caso
A mudança em `app/Http/Controllers/UserController.php@update()` (ramo não-médico) **deixou
de zerar `medico_id`**. Portanto:

- Ao sair de médico para admin/secretária/callcenter, o registro de `medicos` **continua
  vinculado**; `user->medico` segue populado e o CRM/UF/especialidade **permanecem
  visíveis** no painel.
- Ao voltar para médico, `$user->medico` é encontrado e **reaproveitado** — nenhum médico
  novo é criado e nenhum dado é perdido.

Verificação empírica (transação com rollback) no usuário real da Giovana:
```
ANTES: user role=medico medico_id=930 | medico.crm=283163 especialidade=Dermatologista
APOS -> admin (com fix): user.role=admin medico_id=930 | medico ainda existe? SIM crm=283163
user->medico (relacao): crm=283163
```
Sem o fix, o passo "APOS -> admin" trazia `medico_id=NULL` e `user->medico = NULL`.

## Como validar à mão
1. Logado como admin, abra **/users** e edite **Giovana**
   (`giovana.naccarato@revskin.com.br`). Anote o CRM (283163) e a especialidade.
2. Troque o perfil para **Administrador** e salve.
3. Edite a Giovana de novo e troque o perfil de volta para **Médico**: os campos de CRM,
   UF e especialidade aparecem **pré-preenchidos** com os dados originais (não em branco).
4. Salve e confirme que continua tudo lá; a médica também mantém seus pacientes.

Antes da correção, no passo 3 os campos vinham vazios e, ao salvar, era criado um médico
novo vazio (perdendo CRM e pacientes).
