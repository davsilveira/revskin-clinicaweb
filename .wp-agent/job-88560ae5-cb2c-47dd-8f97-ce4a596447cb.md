# Worklog — Análise: cadastro de paciente vinculado a mais de um médico

## O que foi pedido
Estudar duas hipóteses para resolver o bloqueio de cadastro quando um paciente já
tem vínculo com um médico e outro médico tenta cadastrá-lo. Levantar prós/contras e
recomendar a melhor abordagem. **Tarefa de análise — nenhum código de produção foi
alterado.**

## O que foi feito
1. Li o anexo (`01-image.png`): define que Observações, Nº Registro e Indicado Por
   são campos **privados por médico**, e que a 2ª clínica deve ver os dados
   pré-cadastrados mas com esses 3 campos **em branco** (com 2ª tela dedicada).
2. Mapeei a arquitetura atual:
   - `pacientes.medico_id` = FK única (1 paciente = 1 médico).
   - Acesso todo baseado nesse FK (`User::canAccessPaciente`,
     `PacienteController::index/search`).
   - CPF é único **só por regra de validação** (não no banco) → é o que bloqueia o
     2º médico. `codigo` é único no banco.
   - `receitas` já guarda `(paciente_id, medico_id)` → M:N implícito já existe.
3. Medi os dados reais do ambiente `revski-main` (via `artisan tinker`):
   - 1153 pacientes; só 59 com CPF; 0 CPFs duplicados (bloqueados).
   - **11 grupos de nome duplicado entre médicos diferentes (~23 registros)** → a
     duplicação já ocorre hoje de forma descontrolada.
   - 4 pacientes já com receitas de >1 médico no mesmo registro.

## Conclusão / recomendação
**Opção 2 — cadastro único + tabela de vínculo `medico_paciente`** com os 3 campos
privados no pivot. É o que o anexo especifica, elimina a duplicação (dor do admin),
mantém relatórios/integrações corretos e é coerente com o modelo de receitas já
existente. A Opção 1 (registro por médico) só ganha em custo de implementação, mas
oficializa/amplia a duplicação que os dados mostram já existir.

O documento completo (comparativo + esboço de plano de implementação) está em:
`.wp-agent/share/analise-cadastro-paciente-multi-medico.md`
