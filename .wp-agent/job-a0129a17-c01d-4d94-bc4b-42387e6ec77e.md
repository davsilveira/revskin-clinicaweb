## 2. O que realmente acontece (diagnóstico refinado)

O assistente usa **sempre a tabela padrão V16 (id 13)** — confirmei que **não existe nenhuma regra `usar_tabela`** cadastrada, então `RegrasCondicionaisEngine` cai sempre em `TabelaKarnaugh::getPadrao()` = V16. As tabelas 11 e 23.06.25 e 12 (ROSACEA) **não são usadas** hoje pelo assistente.

Reconciliei os 40 códigos distintos da **V16** contra os `produtos.codigo` atuais:

| Situação | Qtde | Observação |
|---|---|---|
| Match exato (já funciona) | 7 | ex.: `DYNAMISEE 3`, `BIONAISSANCE`, `SYNCHRON` |
| **Resolve só normalizando hífen→espaço** | **31** | ex.: `DEMERANE-30G`→`DEMERANE 30G`; `DIA-MAOS`→`DIA MAOS`; `NOITE-MAOS-R0,035H12`→`NOITE MAOS R0,035H12`; `R0,0015H3-NEODELINE-PLUS`→`R0,0015H3 NEODELINE PLUS` |

| Sem match (revisão manual) | 1 | `AQUELANE-8-30G` → catálogo tem `AQUELANE 8` (sufixo `-30G` a mais) |
| Normalizado ambíguo (perigo) | 0 | nenhum código gera casamento duplo → normalização é segura |

**Causa-raiz real (na tabela ativa):** os `produto_codigo` da V16 estão gravados com **hífen como separador** (`DEMERANE-30G`), enquanto o catálogo atual (oList/Tiny) usa **espaço** (`DEMERANE 30G`). O motor casa por **código exato** e, no fallback, por `LIKE '%código-com-hífen%'` — nenhum dos dois normaliza o separador, então 32 dos 40 produtos **não são encontrados** e somem da receita.

Por isso `DYNAMISEE 3` funciona (está gravado com espaço, um dos 7 exatos) e a maioria dos outros não. **Não é o de‑para legado; é diferença de formatação/separador entre o código do Karnaugh e o código atual do produto.**

- Sobre "coloca coisas erradas": no dado atual o `LIKE` não achou substituto errado (os hífens impedem o substring), então o sintoma dominante hoje é **produto sumindo**. O `LIKE '%código%'` continua sendo um **risco latente** de anexar produto errado (ex.: `R0,0015H6` casa com 3 produtos distintos) e deve ser endurecido.

## 3. Detalhe importante do TONALITE (não resolve só com dado)

O template `TONALITE-__-30G` é resolvido em runtime por `RegrasCondicionaisEngine::resolverCodigoTonalite()`, que troca `TONALITE-__-` por `TONALITE-2,5-` → gera `TONALITE-2,5-30G` (com hífen). O catálogo tem `TONALITE 2,5 30G` (espaço). Ou seja, **mesmo migrando o dado, o TONALITE só casa se o motor normalizar o separador**. Portanto o ajuste no motor é necessário de qualquer forma para o TONALITE.

## 4. Plano de correção para produção

Recomendo **duas frentes** (a 1ª é o ajuste durável; a 2ª é a task que você pediu, nos moldes da Giovana):

### Frente A — Endurecer o casamento no motor (correção durável, via deploy)
Em `app/Services/RegrasCondicionaisEngine::buscarProdutoPorCodigo()`:
1. Normalizar separador ao casar: comparar `UPPER(REPLACE(codigo,'-',' '))` colapsando espaços, dos dois lados. Resolve os 31 + o TONALITE de uma vez, sem tocar em dado.
2. **Remover (ou restringir) o fallback `LIKE '%código%'`** para eliminar o risco de anexar produto errado; quando não resolver, logar o código para auditoria em vez de "chutar".

Vantagem: robusto a reimportações futuras (não quebra de novo se o oList mudar formatação).

### Frente B — Task Laravel one‑shot para higienizar os dados (o que você pediu)
Comando novo, seguro (dry‑run por padrão, aplica com `--force`), igual ao padrão do `medicos:reestabelecer-pacientes` da Giovana. Ele reescreve `tabela_karnaugh_produtos.produto_codigo` para o **código canônico exato** do catálogo, deixando o casamento exato/rápido.

Assinatura proposta:
```
php artisan karnaugh:normalizar-codigos-produto
    {--tabela= : limita a uma tabela (default: todas ativas)}
    {--force   : aplica de fato (sem a flag, apenas simula)}
```

Lógica (por linha com `produto_codigo`):
- Se já existe `Produto` com `codigo` == `produto_codigo` (exato) → mantém.
- Senão, normaliza (hífen→espaço, upper, colapsa espaços) e casa contra os produtos normalizados:
  - match único → propõe `produto_codigo = produto.codigo` (canônico).
  - match ambíguo (>1) → **não altera**, lista para revisão.
  - sem match → **não altera**, lista para revisão manual.
- Mapa manual explícito para exceções conhecidas, ex.: `AQUELANE-8-30G → AQUELANE 8`.
- **Não** mexer no template `TONALITE-__-30G` (fica para a Frente A / runtime).
- Rodar dentro de `DB::transaction`, imprimir relatório (alterados / mantidos / ambíguos / sem match) e sempre exigir `--force` para gravar.

> Observação honesta: a Frente B sozinha **não corrige o TONALITE** (resolvido em runtime) nem remove o risco do `LIKE`. Por isso o ideal é **A + B**; se for escolher só uma, a **Frente A** cobre 100% dos casos hoje sem migração de dado.

### Roteiro de deploy sugerido
1. Deployar a Frente A (motor). Já resolve o sintoma em prod imediatamente.
2. (Opcional) Rodar `karnaugh:normalizar-codigos-produto` (dry‑run → conferir relatório → `--force`) para deixar os dados limpos e o casamento exato.
