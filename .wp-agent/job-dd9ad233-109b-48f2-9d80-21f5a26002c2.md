# Worklog — Seção de deploy em produção + rotina de normalização

## O que foi pedido
Prever no plano como subir a Opção 2 em produção e, se houver rotina a executar,
criar um comando Laravel para eu disparar após o deploy (script de normalização de
dados).

## O que investiguei (convenções reais do repo)
- **`.github/workflows/deploy-hostinger.yml`** + **`scripts/hostinger-post-deploy.sh`**:
  deploy roda `artisan down` → `migrate --force` → caches → symlink storage →
  `artisan up`. Logo, **migrations de schema já rodam sozinhas no deploy, sob
  manutenção.**
- **`.github/workflows/reestabelecer-pacientes.yml`**: já existe o padrão de comando
  de dados disparado por `workflow_dispatch` via SSH, **dry-run por padrão + toggle
  `force`** (dispara `medicos:reestabelecer-pacientes`). É exatamente o mecanismo que
  o cliente pediu.
- Comandos existentes (`ReestabelecerPacientesMedico`, `AuditMedicoLinks`) usam a
  convenção dry-run/`--force`.

## Resposta: SIM, há rotina de normalização
A migração de 1153 vínculos para o pivot + checagem de unicidade de CPF não deve ir
escondida numa migration automática — é grande, precisa de dry-run/inspeção e ser
re-executável. Propus **3 comandos Laravel idempotentes** (a criar):
1. `pacientes:opcao2-preflight` — read-only; relata colisões de CPF (trava o
   pipeline), pacientes sem médico, homônimos, e quanto o backfill criaria.
2. `pacientes:backfill-vinculos {--force} {--chunk=500}` — a normalização; upsert no
   pivot por `(medico_id,paciente_id)`; **dry-run por padrão**, aplica com `--force`;
   idempotente.
3. `pacientes:opcao2-verify` — read-only; confere pós-backfill (paridade, sem órfãos,
   sem CPF duplicado); sai ≠ 0 se divergir.
Mais um workflow `opcao2-normalizar-pacientes.yml` (espelhando o de reestabelecer)
para eu disparar preflight/backfill/verify após o deploy.
