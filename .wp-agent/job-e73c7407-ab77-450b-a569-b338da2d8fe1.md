## Situação encontrada

Site retornando **HTTP 500 em tudo**, sem nada no `storage/logs/laravel.log`.

O diagnóstico do usuário ("deve ser uma camada antes") estava próximo, mas os headers da
resposta já entregavam o contrário: `vary: X-Inertia` + cookie `revskin_session` → **quem
respondia o 500 era o Laravel**, não LiteSpeed.

## Causa raiz (uma só, dois sintomas)

`bootstrap/cache/config.php` guarda **caminhos absolutos**. Depois que a Hostinger renomeou a
pasta, os 20 caminhos lá dentro ainda apontavam para
`/home/u368085046/domains/clinicaweb.revskin.com.br/...`:

| Config | Consequência |
|---|---|
| `view.paths` / `view.compiled` | **`View [app] not found` → 500 em toda requisição** |
| `logging…path` | **o log ia para o diretório morto** → por isso o `laravel.log` novo estava vazio |

O erro real estava em
`~/domains/clinicaweb.revskin.com.br/public_html/revskin/storage/logs/laravel.log` (1740 linhas),
arquivo que o Monolog recriou sozinho no caminho antigo:

```
production.ERROR: View [app] not found.
  at .../plataforma.revskin.com.br/public_html/revskin/vendor/.../FileViewFinder.php:138
```

Repare no detalhe que fecha o diagnóstico: o stacktrace aponta para o código em **plataforma**
(o app novo rodando), mas o log foi escrito em **clinicaweb** (caminho do cache velho).

## Segundo problema encontrado (o usuário não tinha visto)

O symlink `public_html/storage` também é absoluto e continuava apontando para a pasta antiga:

```
public_html/storage -> /home/u368085046/domains/clinicaweb.revskin.com.br/.../storage/app/public
```

Isso deixaria **as assinaturas dos médicos em 404** mesmo depois de o site voltar.

## Terceiro problema: `HOSTINGER_REMOTE_PATH` NÃO estava atualizado

O usuário informou ter atualizado, mas `gh variable list` mostrava o valor antigo, com data de
`2026-06-24`. **Corrigido neste job.** Se tivesse ficado assim, o deploy rodaria verde e o rsync
recriaria a pasta antiga sem publicar nada — exatamente a armadilha documentada no job anterior.
